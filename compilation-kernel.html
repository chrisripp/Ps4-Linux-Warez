Compiler son noyau PS4 avec PS4-TOOLS

PS4-TOOLS intègre un onglet dédié à la compilation des bzimages : récupération des sources, application des patchs PS4.(Liverpool/Gladius), puis lancement de menuconfig avant de démarrer la compilation Clang/LLVM Full LTO.

Les menus exacts de l'outil peuvent légèrement changer d'une version à l'autre du script. Le principe reste le même : source → patchs → menuconfig → build. En cas de doute, regarde les vidéos ci-dessous qui montrent le déroulé complet.

Étapes avec PS4-TOOLS

  • Lancer ps4tools-en-final7.sh et ouvrir l'onglet Noyau / Kernel
  • Télécharger ou mettre à jour les sources Kernel
  • Appliquer les patchs supplèmentaires, si nécessaire, le bootargs, si besoin
  • Ouvrir menuconfig vérifier les options requises pour la PS4.
  • Enfin, lancer la compilation Full LTO (Clang/LLVM) une fois la configuration validée
  • Faites preuve de patience, il vous faudra plusieurs essais avant d'avoir un Bzimage complet

Pourquoi compiler pour Jaguar (btver2) et pas en x86-64 générique ?

Le CPU de la PS4 est un AMD Jaguar (8 cœurs, architecture « Puma/Jaguar »). En Clang/GCC, la cible de compilation correspondante s'appelle btver2. Compiler avec -march=btver2 plutôt qu'une cible générique (x86-64, x86-64-v2/v3...) a deux conséquences, une de correction et une de performance :

  • Correction (le plus important) : un noyau compilé en cible générique moderne (ou en -march=native sur une machine de build récente) peut contenir des instructions que le Jaguar de la PS4 ne sait tout simplement pas exécuter (par exemple AVX/AVX2, absentes sur Jaguar). Résultat : crash direct par instruction illégale au démarrage. btver2 garantit que le compilateur ne génère que des instructions réellement supportées par ce CPU.
  • Performance : même pour les instructions communes, -mtune=btver2 ajuste l'ordonnancement du code (latences, largeur d'émission) au pipeline réel du Jaguar, qui est un petit cœur out-of-order à faible fréquence — très différent d'un CPU desktop moderne pour lequel une cible générique serait implicitement optimisée.

C'est exactement ce que règle PS4-TOOLS à ta place : il passe automatiquement KCFLAGS="-march=btver2 -mtune=btver2" au moment du build, sans que tu aies besoin d'éditer de Makefile ou de te souvenir de ces flags à chaque compilation.

LTO et Full LTO : quelle différence ?

Normalement, un compilateur optimise chaque fichier .c du noyau séparément, puis un éditeur de liens assemble les fichiers objets sans grande optimisation supplémentaire. Le LTO (Link Time Optimization) change ça : les optimisations sont reportées à l'étape de liaison, quand le compilateur a une vue sur l'ensemble du code à la fois, ce qui permet de l'inlining et des éliminations de code mort à travers les frontières de fichiers, impossible autrement.

Clang propose deux niveaux :

  • Thin LTO : version parallélisée et incrémentale, rapide à compiler et raisonnable en RAM, avec la majorité du gain de performance du LTO complet.
  • Full LTO : tout le noyau est fusionné en une seule unité de compilation géante et optimisé d'un bloc. C'est le niveau d'optimisation le plus agressif possible (meilleur inlining inter-modules, meilleures décisions du compilateur sur l'ensemble du code), mais au prix d'une compilation beaucoup plus longue et très gourmande en RAM — d'où l'importance du swap évoqué plus haut.

Beaucoup de Developpeurs font ce choix du Full LTO pour tirer le maximum de performance d'un CPU par ailleurs assez faible (Jaguar), quitte à payer le coût en temps et en mémoire au moment de la compilation — un compromis raisonnable puisque le build ne se fait qu'une fois, alors que le noyau tourne ensuite en continu sur la PS4.

Là encore, PS4-TOOLS s'occupe de tout : il active la bonne option LTO_CLANG_FULL dans la configuration du noyau et lance le build avec Clang/LLVM. Tu n'as rien à configurer manuellement pour ça, sauf si tu veux explicitement basculer sur Thin LTO pour des tests plus rapides.

Ce qu'il faut vérifier dans menuconfig pour la PS4

Une fois dans menuconfig, quelques sections méritent une attention particulière pour que le noyau démarre correctement sur PS4 :

Graphique (AMDGPU / GFX7) — indispensable pour Liverpool/Gladius :

Device Drivers --->
  Graphics support --->
    [*] AMD GPU
    [*]   Enable amdgpu support for SI parts (si)
    [*]   Enable amdgpu support for CIK parts (cik)
    [*]   AMDGPU DC - Display Core (DC) support

Liverpool/Gladius est de la famille GFX7 (Sea Islands / CIK) : c'est l'option CIK qu'il faut absolument garder activée.

Bluetooth / Wifi (Marvell 88W8977) :

Networking support --->
  Bluetooth subsystem support --->
    [*] Marvell Bluetooth driver support

Device Drivers --->
  [*] Firmware Drivers --->
    [*] Userspace firmware loading support
  Network device support --->
    Wireless LAN --->
      [*] Marvell WiFi-Ex Driver

Full LTO (Clang) — c'est la base d'un grand nombre de kernel FullLTO :

General setup --->
  Link Time Optimization (LTO) --->
    (X) Clang Full LTO (LTO_CLANG_FULL)

Le ciblage processeur Jaguar ne se fait pas dans menuconfig mais via les flags de compilation, voir la section « Pourquoi compiler pour Jaguar » plus haut. Pas besoin de chercher une option « Jaguar » dans le menu « Processor type and features », elle n'existe pas à ce niveau de granularité.

zram (optionnel, recommandé vu les 8 Go de RAM partagée) :

Device Drivers --->
  Block devices --->
    [*] Compressed RAM block device support (ZRAM)

Lancer la compilation

Une fois menuconfig enregistré (touche S puis Q), PS4-TOOLS prend le relais pour lancer le build Clang/LLVM Full LTO. Selon ta machine, prévoit du temps (et du swap, voir le tutoriel Créer un fichier d'échange swap) : le Full LTO est nettement plus gourmand en mémoire qu'une compilation classique.

Patchs kernel de distributions gaming (CachyOS, Nobara, Bazzite, Drauger OS)

Plusieurs distributions orientées gaming publient leurs patchs kernel en accès libre. Certains (ordonnancement, réactivité, correctifs matériel) peuvent s'appliquer à une PS4 sous Linux, à tester au cas par cas :

DistributionDépôt de patchsNote
CachyOS github.com/CachyOS/kernel-patches Dépôt officiel : ordonnanceurs (BORE, EEVDF...), LTO, correctifs divers, organisés par version de noyau
Nobara wiki.nobaraproject.org/modifications/kernel Nobara part du noyau CachyOS et ajoute ses propres patchs matériel (handheld, manettes...)
Bazzite github.com/bazzite-org/patchwork Dépôt officiel des patchs Bazzite (basé sur le noyau Fedora ARK)
Bazzite (fork PS4) github.com/PfisterFactor/kernel-bazzite-ps4 Fork du noyau Bazzite portant explicitement la mention PS4 dans son nom : à explorer en priorité pour ce projet
Drauger OS github.com/drauger-os-development/kernel-config Configuration et patchs du noyau maison de Drauger OS (basé Ubuntu/gaming)

Ces patchs ne sont pas écrits pour la PS4 : certains s'appliqueront proprement, d'autres non (dépendances matérielles différentes). Toujours tester en --dry-run avant application réelle (voir fonction ci-dessous), et ne jamais patcher un arbre de sources sans sauvegarde.

Fonction pour patcher un noyau (patch -p1)

La plupart des patchs kernel distribués au format git format-patch (dont ceux listés ci-dessus) s'appliquent avec patch -p1 : le -p1 retire le premier niveau de chemin (a/ / b/) généré par git, pour que le patch tombe directement à la racine des sources du noyau.

# À placer dans .bashrc ou un script à part

patch_p1() {
    local patch_file="$1"

    if [ -z "$patch_file" ] || [ ! -f "$patch_file" ]; then
        echo "Usage : patch_p1 chemin/vers/le.patch"
        return 1
    fi

    echo "== Test à blanc (dry-run) : $patch_file =="
    if patch -p1 --dry-run < "$patch_file"; then
        echo "== OK, application réelle =="
        patch -p1 < "$patch_file"
    else
        echo "== Échec du dry-run, patch NON appliqué : $patch_file =="
        return 1
    fi
}

# Variante : appliquer tous les .patch d'un dossier, dans l'ordre
patch_p1_dir() {
    local dir="$1"
    for p in "$dir"/*.patch; do
        patch_p1 "$p" || { echo "Arrêt sur échec : $p"; return 1; }
    done
}

Utilisation, depuis la racine des sources du noyau :

source ~/.bashrc   # si la fonction vient d'être ajoutée

cd ~/kernel-source
patch_p1 ~/kernel-patches/6.15/misc/0001-handheld.patch

# ou tout un dossier de patchs d'un coup
patch_p1_dir ~/kernel-patches/6.15/misc

Si patch -p1 renvoie une erreur de niveau de chemin (fichiers introuvables), essaie -p0 ou -p2 : certains dépôts ne suivent pas exactement la convention a//b/ de git.
